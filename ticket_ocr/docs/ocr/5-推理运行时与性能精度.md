## 11. 推理运行时、CPU/GPU 与 Java 接入

### 11.1 SDK 与底层运行时不是同一职责

1. ORT 接收张量、执行图、返回张量；通常不替你判断这张票据要如何裁剪、如何 CTC 解码或如何关联业务字段。
2. RapidOCR 提供完整 OCR SDK/流水线职责，不宜称其为 JRE。若用 Java 类比，ORT 更接近“执行模型计算的环境”，RapidOCR 更接近“封装任务流程的库”，但模型不是 Java 字节码，二者不是严格 JVM/JAR 映射。
3. 可以绕过 RapidOCR 直接使用 ORT，包括适当的 Java 绑定路线；代价是自行实现输入检查、图像前处理、检测后处理、裁剪、方向处理、识别 batch、字典解码、坐标映射、排序和异常处理。
4. Java 也可以调用 Python 服务，但这涉及 HTTP、并发、超时、安全、数据契约和运维，当前项目尚未实现。入口运行方式统一见 [README](../../README.md)，Python `self`、`main` 等语言知识不属于本手册主线。

### 11.2 CPU、GPU 与 Execution Provider

1. ORT 用 Execution Provider（EP）把计算分配到具体设备或加速库，如 CPU、CUDA 等；可用范围取决于安装包、构建、平台及版本。装了 GPU 并不等于当前程序就在 GPU 上跑。
2. GPU 路线需要兼容的硬件、驱动、CUDA/cuDNN 等依赖、运行时包和 EP 配置；部分算子可能回落 CPU，要核对实际启用的 provider 与执行情况。
3. 小模型、少量图块、低并发时，CPU 可能已经够用；GPU 还涉及启动和数据传输开销。批量更大时可能受益，但不能未经测量宣称快多少倍。
4. CPU/GPU 浮点实现和精度策略可能造成输出差异；精度验收与性能验收都要在目标设备进行。
5. 并发不是越多越快。请求线程、ORT 内部线程、多进程和 batch 可能争抢核心和内存；未确认线程安全前，不能盲目共享引擎并发调用。

<a id="sec-12"></a>
## 12. 相同模型为何结果和速度仍不同

### 12.1 先明确“相同”指哪一层

1. 同名模型不保证同版本；同权重不保证同计算图；同 SHA-256 ONNX 文件不保证同字典、预处理、runtime 和后处理；同单模型输出也不保证同字段结果。
2. 在完全相同的输入张量、图、运行环境、确定性计算和后处理条件下应追求一致输出；条件变化时不能只把差异归为模型“随机”。

| 检查层 | 会引起差异的因素 |
| --- | --- |
| 输入文件/解码 | 文件是否相同、EXIF、透明底、解码器、色彩处理 |
| 模型前处理 | RGB/BGR、NCHW/NHWC、尺寸上限、插值、长宽比、补边、归一化 |
| 模型资源 | Det/Cls/Rec 是否都相同、外部权重、字典及特殊字符 |
| runtime/硬件 | ORT 版本、EP、算子实现、图优化、FP32/FP16/INT8、浮点计算顺序 |
| 模型后处理 | 检测阈值、框扩张、过滤分数、CTC、blank、字典顺序 |
| 流水线 | 裁剪、方向开关、排序、合并、去重、文字行 batch |
| 业务解析 | 标签匹配、同行判定、单位规则、数值格式及拒绝策略 |

3. 级联会放大差异：检测框只差几像素，也可能截掉小数点，改变识别结果，再影响字段关联；不是每次都能用“浮点误差很小”解释业务影响很小。
4. 排查时保存合规的中间信息，按阶段比较输入形状、模型哈希、框、分数、解码和字段，不要只比较最终 JSON。涉及真实图像与文本必须取得访问授权。

### 12.2 性能也不是模型文件单独决定

1. 引擎初始化包含加载模型、建 session 和图优化；应在应用生命周期复用，不要每张图重新加载。文件小不意味着计算少或启动快。
2. 总延迟还包含解码、缩放、裁剪、内存复制、模型执行、解码文字、字段规则和输出。文字行数量会影响 Rec 工作量，不能只按图片张数估计。
3. batch、线程数、CPU 指令集、GPU 传输、动态形状、进程数、日志和磁盘都会影响速度；一个后端模型计算更快，不代表完整流水线更快。
4. 首跑可能含缓存、编译或内存初始化；区分冷启动与预热后的稳态，报告相同计时边界、样本分布、设备、并发、batch 和线程设置。
5. 公平比较需固定文件、模型/字典哈希、配置、精度目标和环境；重复测量并报告波动、延迟分位数、吞吐、内存。不能拿一次带下载的耗时与另一次纯推理对比。
6. 单图耗时倒数不等于生产 QPS；并发还受排队、资源争用和错误处理影响。当前历史样本时间仅是本机运行记录，不是容量承诺。

<a id="sec-14"></a>
## 14. 不准时如何诊断与验收

### 14.1 从低成本、可定位的改动开始

1. **定义问题和指标**：先分清漏检、方向、错字、解码、字段错配和服务异常。保存基线，按错误类型统计，不直接归结为“模型不行”。
2. **修采集**：改善分辨率、失焦、反光、倾斜、压缩和背景；信息已丢失时后处理很难可靠恢复。
3. **检查预处理**：核对 EXIF、透明底、RGB/BGR、尺寸和归一化；纠偏、去噪和增强必须通过回归，过度处理可能抹掉小数点。
4. **调整推理配置**：检测阈值、输入尺寸、方向开关和过滤阈值，记录召回、误检及速度权衡；调参不是训练。
5. **比较适配的预训练模型**：语言、字体、检测/识别任务、模型大小和 CPU 延迟都要合适，不是把下载来的任意模型直接替换。
6. **完善字段规则与校验**：文字正确但关联错时，先修行列、距离、单位、歧义和格式；使用 `Decimal` 等合适类型，不把异常无证据改成正常。
7. **有证据后微调**：已有方案在目标分布稳定失败且有授权数据时，训练出问题的模块；检测错不盲目只训识别器。
8. **最后考虑算法研发**：修改结构、损失、解码或研发专用版面模型，需要更高数据、实验和维护投入，先证明简单方案不足。

这不是必须机械遵循的单一路径：例如字符本身错，字段规则不能修复原图事实。关键是按阶段定位，而不是花最多成本后再找原因。

### 14.2 业务验收必须比“能识别”严格

| 指标 | 衡量什么 | 边界 |
| --- | --- | --- |
| 检测 precision/recall | 框是否正确、是否漏掉 | 不证明框内文字正确 |
| 字符错误率 CER | 插入、删除、替换等字符错误 | 平均好不代表关键数字全对 |
| 文字行/数字整串正确率 | 整个目标字符串完全匹配 | 一位错、小数点错都应算错 |
| 字段精确匹配率 | 值、单位、归属组等按契约正确 | 需明确空值、多组与标准化规则 |
| 拒绝/人工复核率 | 系统有多少结果不自动接受 | 应与自动接受结果的错误率一起看 |
| 性能及稳定性 | 延迟、吞吐、内存、错误率 | 应包含目标并发和完整流程 |

1. 票据数字特别关注整串、小数点、负号、位数、单位和多组归属；字符平均准确率再高，也不能推导每个业务值可靠。
2. OCR 分数阈值只是启发式，需在业务数据校准。应允许“不知道”、拒绝和人工确认，不能为追求覆盖率把缺失补零。
3. 校验可以发现异常，不一定能证明正确：格式合法的错误数字仍可能通过。拒绝率降低也不一定是进步，可能只是放过更多错误。
4. 不承诺完美识别。验收要有代表性测试集、样本量、错误代价、覆盖范围和回滚方案；真实样本与完整结果只在授权环境处理。

## 8. PaddleOCR、PP-OCR 与 RapidOCR

### 8.1 PaddleOCR 提供的是一套成果，不只是一个模型

1. **PaddlePaddle**是底层深度学习框架；**PaddleOCR**是建立在相关生态上的 OCR/文档处理项目和工具体系，可能提供算法实现、数据工具、训练、评估、导出、推理、配置、字典、预训练权重及文档。
2. `paddleocr` Python 包是使用这套体系的一种入口，不等于整个项目，也不等于一个固定网络。项目不同版本的模块、依赖、模型和调用方式可能变化。
3. 网络与训练代码提供“怎么学”；预训练权重提供“已经学到的数值结果”；导出推理制品提供“怎么部署”。不必为了使用成果再训练一遍，但仍要配对正确文件和配置。
4. **PP-OCR**是其中的 OCR 系列和配套方案。检测、方向分类、识别可能来自不同代际与大小；语言、字典、输入输出及解码要求不同，系列名相同不代表任意可混搭。
5. PaddleOCR 也不能严格等同 Java 的 Spring。它包含算法、模型成果及任务流水线，不只是应用依赖注入或 Web 框架；类比仅用于理解职责，不应强套产品层级。

### 8.2 RapidOCR 是独立推理流水线

1. RapidOCR 是 OCR SDK/流水线，负责输入处理、模型调用、裁剪、解码及结果组合；可以适配 PP-OCR 等模型，不是简单转调 `paddleocr` 包的别名。
2. 它可使用已经转换好的模型，部署方不必安装完整训练工具或重新转换。提供适配和分发，不等于它训练了每个模型。
3. RapidOCR 不等于 ONNX Runtime。前者知道 OCR 流程，后者负责模型图计算；后端选择取决于 RapidOCR 版本、安装依赖、模型格式及配置，不能说永远只有 ORT 一种。
4. 更换 SDK 不一定更换权重；更换权重也不一定更换 SDK。必须区分“模型能力”和“流水线适配能力”。

纯文本职责链：

```text
算法/训练实现（如 PaddleOCR） + 训练框架（如 PaddlePaddle） + 数据
→ 训练权重/配置 → 推理导出与必要转换 → 适配模型
→ RapidOCR 组织 OCR 流程 → ORT 等后端执行模型计算 → 文字/坐标/分数
→ 本项目字段规则 → 将来按契约接入 Java
```

这是一种典型关系，不是当前三个文件完整训练来源链的已核实证明。

## 9. 权重、checkpoint、推理制品与 ONNX

### 9.1 模型到底是什么文件

| 名称 | 内容和职责 | 不能据此推断的事 |
| --- | --- | --- |
| 网络结构 | 层、连接和计算方法，可用代码或图描述 | 不包含完整学习结果也可定义结构 |
| 权重文件 | 参数数值，常需匹配网络代码 | 不是完整应用，不保证可独立运行 |
| 训练 checkpoint | 权重及可能的 optimizer、步数等状态 | 不保证每个 checkpoint 都保存全部续训信息 |
| 导出推理制品 | 部署计算图、参数及相关元信息 | 通常不是原始可完整续训状态 |
| ONNX | 模型交换格式，通常描述计算图、算子和权重 | 不是训练框架，也不是运行引擎 |
| 字典与配置 | 类别映射、输入约定、网络或后处理设置 | 不匹配会让正确分数解出错误文字 |

1. 权重是学到的数值参数，不是逐条查询训练图片的数据库，也不是可直接阅读的业务源码；但模型可能记忆训练信息，仍需隐私审查。
2. ONNX 参数既可能放在文件内，也可能使用外部数据文件。不能永远假定“一个 `.onnx` 就已带齐所有资源”。
3. `.onnx` 表示一种制品格式，不能凭扩展名推断最初用 PyTorch、PaddlePaddle 还是 TensorFlow 训练，更不能据文件名证明训练方、训练数据与许可。
4. “权重相同”与“文件相同”不是同义词：元数据、图结构、序列化方式、算子融合不同，文件哈希可能不同；只核对部分权重相同也不足以证明模型行为一致。
5. 同一文件 SHA-256 匹配可以确认文件内容一致，但不能证明模型质量、许可合规、来源真实性或整个流水线一致。

### 9.2 多框架可以通过 ONNX 衔接部署

```text
PyTorch / PaddlePaddle / TensorFlow 等训练生态
→ 各自支持的导出步骤或转换器（如 Paddle2ONNX 等）
→ ONNX 图及权重（必要时含外部数据）
→ ONNX Runtime 等兼容引擎 → 输出张量 → 任务解码
```

1. ONNX 像交换协议，不是“保证所有模型通吃”的万能容器。要检查 exporter、opset、动态形状、自定义算子、控制流、数据类型和目标执行提供程序支持。
2. 转换一般不是重新训练，不会自动学会字体；也可能发生图优化或数值差异，需做转换前后回归。量化是另一个明确步骤，不能把普通格式转换都叫量化。
3. ORT 主要用于推理，但其生态也存在训练相关能力；说“ORT 绝不支持训练”不准确。这不等于任意部署 ONNX 都能无条件在原框架继续微调。
4. 单独拿 ONNX 直接运行，需要掌握输入名、形状、布局、预处理、输出语义及字典。运行成功只证明能计算，不证明解码和 OCR 流程正确。

## 10. 一张图片的 OCR 全流程

### 10.1 典型的检测加识别方案

```text
读图与 EXIF/透明通道处理 → 检测前处理 → Det 找文字区域
→ 映射回原尺寸并筛选框 → 透视裁剪/阅读顺序整理
→ 可选 Cls 判断有限方向并旋转 → Rec 前处理及识别
→ 字典/CTC 等解码 → 文字 + 框 + OCR 分数
→ 标签/位置/单位关联 → 业务字段 + 状态 + 证据
```

| 阶段 | 解决的问题 | 典型错误 |
| --- | --- | --- |
| 采集/解码 | 是否有足够可见信息 | 失焦、反光、方向/透明底不当 |
| Det 检测 | 文字在哪里 | 漏框、粘连、框截断 |
| 裁剪/纠正 | 识别图块是否完整且方向合适 | 笔画裁掉、透视未纠正 |
| Cls 方向 | 有限类别内是否倒置 | 方向类型不支持、误旋转 |
| Rec 识别 | 图块写了什么 | 易混字、小数点、单位误读 |
| 解码/排序 | 输出类别如何变成有序文字 | 字典错配、读序错误 |
| 业务解析 | 哪个标签对应哪个值 | 跨行串组、单位错配、多候选歧义 |

1. 当前项目使用的旧式文字行分类模型针对 **0/180 度**方向，不是任意角度校正器，也不能代替整页版面方向检测。其他模型可能有更多类别，应看具体模型而非仅看 `Cls` 名称。
2. 识别器常输出逐时间步字符类别分数；CTC 解码常涉及重复折叠与 blank 处理，但不是所有 OCR 都用 CTC，也不是所有识别器都自回归生成。
3. 字典顺序、特殊类别和空格设置必须匹配。文件存在、不报错不代表字典正确；错误字典能把分数稳定映射成错误字符。
4. 检测漏掉的区域没有进入识别器，因此不能只换 Rec 就期待补回漏检。图像信息已丢失时，也不能指望更大的模型必然还原事实。
5. 坐标需明确对应哪张图、是否经过 EXIF 归一化、如何缩放回去；整框坐标不能伪造成字符级证据。
6. OCR 分数不是经过业务校准的“字段正确概率”。高分可能错字，也不能证明标签和值配对正确；低分过滤还会降低召回。

### 10.2 OCR 与业务字段解析分开

1. “识别出总累计及一个数字串”属于 OCR 文字结果；“判断该数字串属于哪个总累计标签”属于字段关联。两者都正确才得到可信业务字段。
2. 字段规则可用行列、距离、单位、格式和业务约束，但不能无证据地把字母猜成数字、把异常值改得合理、把多组数值自动相加。
3. 保留文字、框、分数和字段证据供授权复核；缺失、歧义、低分、格式异常和服务失败应分别表达，不能都返回零。
4. Java 调用方需要稳定字段契约，但契约不应隐藏不确定性。当前本地 Demo 的字段和状态不是已确认生产接口。

# 项目需求

## 已确认

1. 项目定位为 Python 票据 OCR 服务。
2. 调用方为 Java 后端服务。
3. 支持接收图片或图片地址，返回结构化解析结果（服务目标，当前尚未实现）。
4. 用户最新要求直接运行识别 `test_file/` 内容，不要复杂参数 Demo；无参数处理项目根目录该文件夹的顶层图片，保留显式单图兼容，不扩展 HTTP。
5. Demo 默认不下载模型，提供显式下载开关；图片留在本地，终端不显示完整识别文字和图片路径，JSON 保存文字、坐标、置信度和耗时。

## 本轮最小解析范围

1. 根据用户重新核对图片、调整程序的请求，Demo 仅新增“总累计”提取；定位全部精确标签，按左标签、右侧同行数值配对，多组按版面顺序输出，不自动相加。保留原 OCR 明细，不将“总累计报表”当目标标签。
2. 支持标签数值同框与单位拆框；十进制字符串和单位分别保留，不将重量推定为金额。缺失、歧义、格式异常、低 OCR 置信度均待确认；输出框供复核，不跨行串组、不复用数值候选。
3. 这些是本轮本地 Demo 实现范围；字段名、状态及阈值不是已确认的生产接口契约，具体格式和当前限制见 [README](../README.md)。

## 待确认

1. 票据类型、语言、样本来源及需要提取的字段。
2. 开发和部署操作系统、Python 运行条件、CPU/GPU 及可用资源。
3. 本地 OCR 或云端 OCR、数据出网限制、预算及模型许可证要求。
4. 图片格式、大小、页数、批量需求及图片 URL 的来源与访问权限。
5. 接口路径、请求方式、字段命名、空值、金额、时间和错误码契约。
6. 同步或异步调用、超时、并发量、延迟和识别准确率目标。
7. 服务认证、网络访问范围、原图与识别结果的保存和删除策略。

## 确认顺序

1. 先确认票据类型、部署环境和 CPU/GPU，再进行 Python 与 OCR 引擎的兼容性选型。
2. 再确认接口契约、性能目标和数据安全边界，最后进入最小可用实现。
3. 需求确认后更新本文；技术选型结论另记入[决策记录](../.agents/memory/decisions.md)。

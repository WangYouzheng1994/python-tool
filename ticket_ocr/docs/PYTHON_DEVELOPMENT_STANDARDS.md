# Python 开发规范

> 适用范围：票据 OCR 服务及其公共 Python 模块。服务面向 Java 后端，接收图片文件或图片 URL，返回结构化识别结果。
>
> 本文依据 Python 社区通用实践制定，是本项目的团队规范，不代表存在一份适用于所有公司的统一“行业标准”。文中的技术选型为新建服务的推荐基线，只有完成项目配置后才视为实际启用。

## 1. 规范等级与基本原则

- **必须**：提交和发布前应满足；例外须在 PR 中说明原因、影响和补救措施。
- **建议**：默认遵守，存在明确收益时可以调整。
- **可选**：根据业务规模引入，避免过度设计。
- 优先保证正确性、可读性、可测试性和安全性，再基于测量优化性能。
- 业务规则与 Web 框架、OCR 引擎、存储和网络客户端解耦。
- 禁止在导入模块时下载模型、连接外部服务或执行耗时初始化。

## 2. 运行环境与依赖管理

### 2.1 Python 版本

- 新项目建议使用 Python 3.12 或更高的受支持稳定版本，最终版本必须通过 OCR 引擎、推理框架和部署环境的兼容性验证。
- 在 `pyproject.toml` 中声明 `requires-python`，开发、CI 和生产保持相同的 Python 次版本。
- 必须使用独立虚拟环境，不依赖全局安装的包。
- CPU 和 GPU 推理环境应分别验证；GPU 环境记录驱动、CUDA、推理框架和模型版本。

### 2.2 包与依赖

- 使用 `pyproject.toml` 管理项目元数据、构建配置和工具配置。
- 新项目建议使用 `uv` 管理环境及依赖，使用锁文件保证应用部署可复现；已有工具链不应无收益地迁移。
- 运行依赖与开发依赖分组管理；只在测试中使用的库不得加入生产依赖。
- 禁止提交 `.venv/`、下载的模型、缓存、凭据或本地环境文件。
- 第三方依赖必须评估许可证、维护状态和安全风险；升级依赖后执行回归测试。
- 应用交付使用锁定依赖；若发布可复用库，声明合理的依赖范围并测试支持的版本组合，不强行锁死调用方的全部依赖。

## 3. 项目结构

建议采用 `src` 布局，以下为目标结构示例，并非当前实现清单：

```text
ticket_ocr/
├── pyproject.toml
├── uv.lock
├── README.md
├── .env.example
├── src/
│   └── ticket_ocr/
│       ├── __init__.py
│       ├── main.py              # 应用创建、启动与生命周期
│       ├── api/                 # HTTP 路由及协议转换
│       ├── schemas/             # 请求、响应数据模型
│       ├── services/            # 识别流程编排
│       ├── domain/              # 票据领域模型、规则与异常
│       ├── engines/             # OCR 引擎适配
│       ├── infrastructure/      # HTTP、存储等外部依赖适配
│       └── core/                # 配置、日志等基础能力
├── tests/
│   ├── unit/
│   ├── integration/
│   └── fixtures/                # 脱敏且具备使用权限的样本
└── docs/
```

- 路由层只负责参数校验、调用服务和返回响应，不直接实现 OCR 或票据解析规则。
- 服务层编排下载、校验、识别和结构化解析；领域规则不得依赖 Web 框架。
- 引擎通过清晰接口适配，业务层不直接依赖某个 OCR 厂商的原始返回结构。
- 避免创建无明确职责的 `utils.py` 大文件；模块按业务能力命名。
- 小型服务可以合并职责单一的目录，不为满足目录数量引入空层和空抽象。

## 4. 代码风格与命名

- 遵守 PEP 8；建议使用 Ruff 统一检查和格式化，行宽统一为 100。
- 使用 4 个空格缩进，文件编码为 UTF-8。
- 模块、函数、变量使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`。
- 包名使用小写并尽量简短；禁止与 `json`、`typing`、`http` 等标准库模块重名。
- 使用绝对导入，导入按标准库、第三方库、项目代码分组，由工具排序。
- 禁止通配符导入、无意义缩写和通过 `sys.path` 修改解决包导入问题。
- 函数应职责单一，优先使用提前返回减少嵌套；复杂逻辑拆分为有业务含义的小函数。
- 使用上下文管理器管理文件、锁和连接；临时文件必须在成功、失败和取消路径下清理。
- 不使用可变对象作为默认参数；禁止用 `assert` 代替业务输入校验。
- 注释解释“为什么”，避免重复代码含义；公开接口提供说明参数、返回值和异常的文档字符串。
- 项目说明和注释建议使用中文；标识符使用准确的英文，协议字段统一使用英文。

## 5. 类型与数据模型

- 公开函数、跨模块接口和核心业务函数必须标注参数及返回类型。
- 推荐使用 `list[str]`、`dict[str, str]`、`str | None` 等现代类型写法。
- 严格限制 `Any`；不确定的外部数据先校验，再转换为内部模型。
- HTTP 边界建议使用 Pydantic 模型，内部简单数据对象可使用 `dataclass`。
- `None`、空字符串、空数组和数值零必须具有明确且不同的业务含义。
- 金额使用 `Decimal`，禁止用二进制浮点数进行金额计算；JSON 金额建议传十进制字符串，并明确币种、精度与舍入规则。
- 日期采用 ISO 8601；时间戳必须带时区，内部建议统一为 UTC。
- 字段名、长度、枚举、可空性和默认值必须通过模型显式定义。

## 6. HTTP API 与 Java 对接

### 6.1 接口设计

- 新建服务建议采用 FastAPI 和 Pydantic，并生成 OpenAPI 文档。
- API 使用显式版本，例如 `/api/v1/ocr/recognize`。
- 文件上传使用 `multipart/form-data`；URL 识别使用 JSON 请求。建议提供独立路由，避免同一路由混用不明确的媒体类型。
- 必须校验输入数量、文件大小、图片格式、像素数量和 URL；具体上限由配置定义并写入接口文档。
- 明确识别超时、请求并发限制和服务容量；长任务按需使用异步任务接口，不让连接无限等待。
- 同步识别通常不应默认自动重试；如引入异步提交或收费操作，应定义幂等键、作用范围和有效期。

### 6.2 响应契约

- Java 与 Python 两端在联调前确认字段命名、类型、可空性、金额、时间和枚举定义。
- JSON 建议统一使用 `snake_case`；Java 端通过序列化映射适配。已有契约优先，禁止擅自更改。
- 成功响应应包含请求标识和结构化结果；按需提供票据类型、字段置信度、模型版本和质量提示。
- 缺失字段返回 `null`，不得伪造金额、日期或票据号码。
- 置信度只有在引擎提供或存在经验证的计算规则时才返回；明确取值范围及含义。
- 错误响应统一包含稳定错误码、可读消息和请求标识；不得返回内部堆栈、文件路径、密钥或完整原始图片地址。
- HTTP 状态码应表达真实结果：参数错误使用 `400/422`，超大请求使用 `413`，不支持的媒体类型使用 `415`，限流使用 `429`，内部错误使用 `500`，依赖不可用使用 `503`。不得把全部异常包装成 `200`。
- “未识别到内容”“不支持的票据”“识别质量不足”和“服务异常”必须分别定义，不得混为一类。
- 新增兼容字段可在原版本迭代；删除字段、改变类型或语义属于破坏性变更，必须提供迁移方案。

## 7. OCR 与图片处理规范

- 处理流程建议为：输入校验 → 安全获取图片 → 解码与预处理 → OCR → 字段提取 → 业务校验 → 响应组装。
- 根据解码结果验证真实图片格式，不能仅信任扩展名或 `Content-Type`。
- 限制压缩文件大小、解码后像素数、帧数和资源占用，防止解压炸弹及恶意图片耗尽资源。
- 明确 EXIF 方向、多页图片、透明背景和超大分辨率的处理策略；未支持的格式应显式拒绝。
- 保留必要的原始文本与位置信息用于受控调试，默认不通过普通业务响应或日志暴露全部内容。
- 字段标准化不得无依据地修改识别内容；对金额、日期和票号的修正应具备明确规则与测试。
- 质量评估区分文字识别准确率、字段提取准确率和整票通过率，不能仅用“接口调用成功率”衡量效果。
- 模型与词典必须版本化，记录来源、许可证和校验值；禁止在生产请求链路中临时下载模型。
- 加载模型应在生命周期中受控执行；确认引擎线程安全性，未确认前不得共享实例并发推理。

## 8. 异步、并发与性能

- `async def` 适用于异步 I/O，不会自动使 CPU/GPU 推理变为非阻塞。
- 禁止在事件循环中直接执行阻塞下载、大文件读写或长时间推理；根据引擎特点使用受限线程池、进程或独立推理服务。
- 所有队列、执行池和并发任务必须有容量上限，并定义排队超时与过载响应。
- HTTP 客户端应复用连接池，并设置连接、读取和整体处理时限。
- 下载与解码必须限制内存占用，避免多次复制大图片。
- 多进程会复制模型内存；工作进程数必须结合 CPU、内存和 GPU 显存评估，不照搬通用公式。
- 优化前记录基线，关注吞吐量、P50/P95/P99 延迟、排队时间和资源占用。

## 9. 异常、日志与可观测性

- 定义明确的业务异常，在统一异常处理层映射为 HTTP 响应。
- 禁止裸 `except:`；广泛捕获 `Exception` 只用于确有必要的边界，必须记录并转换或重新抛出，不得静默吞错。
- 重抛保留异常链，例如 `raise ImageDownloadError(...) from exc`。
- 日志使用标准日志接口或统一封装，禁止使用 `print` 作为生产日志。
- 建议输出结构化 JSON 日志，包含时间、级别、服务名、环境、请求标识、阶段、耗时和错误码。
- 请求标识必须贯穿 Java 调用、Python 服务和外部依赖；外部传入的标识需限制长度及字符集。
- 禁止记录图片内容、身份证号、银行账号、完整票据文本、访问令牌或带签名参数的 URL。
- 指标标签禁止包含请求标识、图片 URL 等高基数数据。
- 区分存活检查与就绪检查；模型未加载或必要依赖未就绪时，不应报告可接收识别流量。

## 10. 安全与数据保护

### 10.1 图片 URL 与 SSRF 防护

- 仅允许明确支持的协议，生产建议仅允许 HTTPS；拒绝 URL 内嵌用户名密码。
- 优先使用业务方受控的域名白名单或对象存储标识，而不是任意互联网 URL。
- 必须阻止回环、私有、链路本地、保留地址和云元数据地址，覆盖 IPv4、IPv6 及其映射形式。
- 校验 DNS 解析结果，并确保实际连接目标受到同样限制，防止 DNS 重绑定；不能只校验 URL 字符串。
- 默认关闭自动重定向；确需跟随时，对每一跳重新执行协议、域名和目标地址校验，并限制跳转次数。
- 结合出口网络策略限制访问范围；应用校验不能替代网络隔离。
- 流式下载并限制实际接收字节数，不能仅依赖 `Content-Length`；同时设置超时。

### 10.2 服务与数据安全

- 服务接口必须有适合部署环境的认证与授权，不因运行在内网就默认可信。
- 按调用方限流并限制并发；凭据使用环境变量或密钥管理系统，禁止写入源码与镜像。
- `.env.example` 只提供占位符；实际 `.env` 不提交。
- 图片和识别结果按敏感数据管理，定义用途、访问权限、保存期限和删除策略；默认不长期保存原图。
- 用户文件名不得直接拼接路径，临时文件使用随机名称并存放于专用目录。
- 禁止对不可信输入使用 `eval`、`exec`、不安全反序列化或未经约束的 shell 命令。
- 容器尽量以非 root 用户运行，使用最小权限和受控可写目录。

## 11. 测试规范

- 使用 pytest；测试默认不得依赖公网、生产账号或真实客户数据。
- 单元测试覆盖字段解析、标准化、校验和异常分支；通过依赖注入替换 OCR 引擎和下载器。
- 集成测试覆盖接口、模型校验和外部适配；真实模型测试单独标记，明确模型与硬件要求。
- Java 对接必须有契约测试，检查字段、类型、错误码、金额精度及空值语义。
- 必测输入包括：空文件、损坏图片、伪造格式、超大图片、无文字、低置信度、下载超时、重定向、SSRF 地址和引擎失败。
- 测试文件使用 `test_*.py`，测试命名体现条件和预期结果。
- 新增逻辑必须具备测试；覆盖率作为辅助指标，关键规则和失败分支不能仅依赖覆盖率数字判断。
- OCR 质量回归使用有使用权限的脱敏固定样本集，记录数据集版本、模型版本、指标和误差容忍范围。
- 性能测试与日常单元测试分开运行，记录测试环境和并发条件。

## 12. 工具链与质量门禁

推荐基线：

| 用途 | 工具 |
| --- | --- |
| 环境和依赖 | uv |
| 格式化与静态检查 | Ruff |
| 类型检查 | mypy |
| 测试与覆盖率 | pytest、pytest-cov |
| 依赖漏洞检查 | pip-audit 或组织统一工具 |
| 提交前检查 | pre-commit，可选 |

在相应依赖和配置已添加后，建议以以下命令作为 CI 基线：

```bash
uv sync --locked --group dev
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest --cov=ticket_ocr --cov-report=term-missing
```

- 上述命令是目标约定，不表示当前仓库已安装工具或存在对应配置。
- CI 必须使用锁文件；格式、静态检查、类型检查和测试失败时不得合并。
- 必须定期执行依赖漏洞检查，并为风险接受记录负责人和到期时间。
- 忽略规则必须限定范围并说明原因，禁止全局关闭检查以掩盖问题。

## 13. 配置、部署与发布

- 配置集中管理，在启动时校验；配置错误应尽早失败，不得带着无效配置接收流量。
- 开发、测试和生产配置隔离；通过环境变量注入，不在业务代码内判断个人电脑路径。
- 明确请求大小、下载时限、推理时限、并发数、模型路径和临时目录等参数。
- 镜像、代码和模型分别标记版本，部署时记录可追溯组合。
- 生产关闭调试模式；接口文档按访问策略受控开放。
- 服务支持优雅关闭：停止接收新任务，在有限时间内处理或取消在途请求并释放资源。
- 发布必须有回滚方案；涉及响应契约或模型变化时，分别验证兼容性和识别质量。

## 14. Git 与代码评审

- 每个提交聚焦一个逻辑变更，不混入无关格式化和生成文件。
- 提交信息建议使用 `feat:`、`fix:`、`docs:`、`test:`、`refactor:`、`chore:` 等前缀。
- PR 必须说明变更目的、实现要点、测试结果、兼容性影响和配置变更。
- 未执行的测试必须如实说明，不得将“已编写测试”描述成“已通过测试”。
- 不提交客户票据、密钥、模型大文件、个人 IDE 配置或运行日志。
- 评审重点为业务正确性、输入边界、安全、资源使用和可维护性，而非人工争论格式。

## 15. 交付检查清单

- [ ] 公开接口有类型标注，参数和响应具备明确模型。
- [ ] 文件与 URL 输入经过安全校验，资源占用有上限。
- [ ] 错误码、HTTP 状态、金额和时间格式与 Java 端契约一致。
- [ ] 阻塞推理不会直接占用异步事件循环，并发与队列有界。
- [ ] 日志可追踪且不泄露敏感数据。
- [ ] 单元、集成及必要的契约和质量回归测试已通过。
- [ ] 格式、静态检查和类型检查已通过。
- [ ] 配置、依赖、模型版本及部署回滚方式已记录。
- [ ] README 包含安装、启动、测试、请求示例和限制说明。
